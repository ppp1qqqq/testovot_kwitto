## Как ставил задачу

Первый запрос был со всем контекстом: приложил PDF с заданием целиком и попросил сделать его аккуратно, перепроверять себя и опираться на тесты. Ещё попросил, чтобы README, этот файл и комментарии в коде читались как написанные человеком. Пример из задания (`1990000` на 3 месяца даёт `[663334, 663333, 663333]`) сразу стал отдельным тестом.

Второй запрос, уже по готовому коду, был коротким: «перепроверь еще раз все». Ассистент заново прочитал каждый файл, погонял сервер странными входными данными и повторил проверку тестов поломками кода.

## Где модель ошиблась и как это всплыло

Первый набор из 81 теста прошёл с первого запуска, и это насторожило. Ассистент по очереди ломал код (копейки в конец графика, округление вниз, регистр промокода, лишний переход статуса, формат 409) и смотрел, упадут ли тесты. Не упали только в одном случае: если убрать поиск по `Idempotency-Key`, дубль всё равно ловил unique-индекс. Значит, гонку двух одинаковых запросов не проверял ни один тест. Теперь её имитирует отдельный тест через monkeypatch.

Подпись вебхука сравнивалась через `hmac.compare_digest` на строках. На не-ASCII символах функция бросает `TypeError`, и `X-Signature: é` давал 500 вместо 401. Теперь сравниваются байты. Ещё по мелочи: фильтр `?email=` зависел от регистра (`EmailStr` приводит к нижнему регистру только домен), а пустой `promo_code: ""` давал 422.

Повторная проверка нашла ещё два бага. Id больше 64 бит (`/payments/99999999999999999999`, огромный `tariff_id`, `payment_id` или `offset`) доходил до SQLite и ронял запрос с 500. Пустой `Idempotency-Key` склеивал все такие запросы в один платёж, то есть следующий покупатель получил бы чужой платёж. Оба случая теперь отсекаются на валидации с 422. Заодно нашлась проверка без теста: `UPDATE ... WHERE status = <прочитанный>`, которая не даёт двум одновременным вебхукам затереть друг друга. Тест на неё есть, и он падает, если условие убрать.
